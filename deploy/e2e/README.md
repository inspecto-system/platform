# Сквозной сценарий CP2

`cp2.sh` проходит путь пользователя через API (T-207): регистрация и вход → объект, помещение,
осмотр с чек-листом → дефект → загрузка фото в media-service (поворот по EXIF, повтор с
`Idempotency-Key`) → привязка к наблюдению → доступ чужого пользователя (`404`) → повторный
осмотр и «устранён» → PDF-отчёт завершённого осмотра в report-service (до завершения — `409`,
чужому — `404`, файл начинается с `%PDF-`) → отвязка фото и его удаление заданием outbox →
удаление объекта вместе с фото и отчётами → удаление аккаунта.

`nginx.sh` проверяет точку входа (T-505): HTTP → HTTPS, заголовки безопасности (SEC-09), маршруты к
core, media и report через один хост, веб-приложение на `/` с единственной (своей) CSP с nonce, `404` для `/internal/**` и актуаторов (в том числе через `../`),
лимит тела (`413`) и частоты входа (`429 RATE_LIMITED` с `Retry-After`). `cp2.sh` идёт к сервисам
напрямую: его входы с одного IP упёрлись бы в лимит частоты, который проверяет `nginx.sh`.

`run.sh` запускает оба сценария, а затем проверяет снаружи, что в базах core, media и report и в бакетах `photos` и
`reports` SeaweedFS не осталось ничего от удалённого аккаунта и удалённого объекта.

Запуск (нужны клоны `core-service`, `media-service`, `report-service` и `web` рядом с `platform`; в
Git Bash — с `MSYS_NO_PATHCONV=1`):

```bash
docker compose -f deploy/compose.dev.yaml --env-file deploy/.env --profile apps up -d --build --wait
sh deploy/e2e/run.sh
```

Сценарий выполняется в одноразовом контейнере в сети `services`, поэтому одинаково работает
локально и в CI (`.github/workflows/e2e.yml`: каждый день, вручную и при изменении `deploy/`).
