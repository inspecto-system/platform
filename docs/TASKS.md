## Неделя 1 — CP0: проектирование и инфраструктура

### T-001 · Документация проекта и журнал решений — `DONE`

- [platform] **Описание:** создать `docs/` со всеми обязательными документами, зафиксировать ADR-001…021.
- **Цель:** единый источник актуального состояния проекта между сессиями.
- **Зависимости:** —. **Оценка:** 1.
- **Готово, когда:** все документы созданы, согласованы между собой, PR слит.
- **Проверка:** ревью владельца; markdownlint в CI.

### T-002 · Предварительный архитектурный PDF — `DONE`

- [platform] **Описание:** диаграммы (Mermaid), подробное описание архитектуры, воспроизводимая сборка `INSPECTO_SYSTEM_ARCHITECTURE.pdf`.
- **Цель:** требование 8.1, версия этапа проектирования.
- **Зависимости:** T-001. **Оценка:** 1.
- **Готово, когда:** PDF собирается одной командой, содержит оглавление, нумерацию страниц, подписи рисунков, легенду.
- **Проверка:** PDF открывается, текст извлекается, диаграммы читаемы при печати A4.

### T-003 · OpenAPI-контракты v0.1 — `DONE`

- [platform] **Описание:** `api/core.yaml`, `api/media.yaml`, `api/report.yaml`, `api/ml.yaml`, общие схемы ошибок (RFC 9457), пагинации, идентификаторов.
- **Цель:** contract-first разработка серверов и клиентов (ADR-014).
- **Зависимости:** T-001. **Оценка:** 1,5.
- **Готово, когда:** спецификации проходят Spectral lint и проверку ссылок; соответствуют API_DOCUMENTATION.md; после слияния поставлен тег `api-v0.1.0`.
- **Проверка:** CI (Spectral); ревью.

### T-004 · Переиспользуемые CI-шаблоны — `DONE`

- [platform] **Описание:** reusable workflows для Java и Go и общий workflow безопасности (Gitleaks, Dependency Review, CodeQL); общие конфиги линтеров. Workflow для Android, Web и Python добавляются в T-304, T-501, T-601.
- **Цель:** единые правила качества для всех репозиториев (CODE_QUALITY.md).
- **Зависимости:** T-001. **Оценка:** 1 (дальше дополняются по мере появления компонентов).
- **Готово, когда:** шаблоны вызываются из сервисных репозиториев; падение любой проверки делает PR неготовым.
- **Проверка:** тестовый PR с намеренной ошибкой форматирования проваливает CI.

### T-005 · docker compose для разработки — `DONE`

- [platform] **Описание:** `deploy/compose.dev.yaml`: PostgreSQL 16 (три базы, по два пользователя на базу, только TLS), SeaweedFS S3 (два бакета, идентичность на сервис), Gotenberg (Chromium без сетевого доступа); `.env.example`; smoke-тест в CI.
- **Цель:** воспроизводимая инфраструктура одной командой.
- **Зависимости:** установлен Docker. **Оценка:** 0,5.
- **Готово, когда:** `docker compose up` поднимает все компоненты, healthcheck зелёный.
- **Проверка:** запуск у владельца проекта; подключение к каждой базе своим пользователем.

### T-006 · Каркас core-service — `DONE`

- [core-service] **Описание:** Spring Boot / Java LTS / Gradle (Kotlin DSL); точные версии выбираются по TECH_STACK.md §2, структура пакетов, Flyway, Spotless, Checkstyle, PMD, SpotBugs, JaCoCo, health endpoint, CI.
- **Цель:** основа для CP1, стандарты качества с первого коммита.
- **Зависимости:** T-004. **Оценка:** 1.
- **Готово, когда:** сборка и все проверки зелёные; приложение стартует с Testcontainers.
- **Проверка:** CI; `./gradlew check`.

### T-007 · Защита веток во всех репозиториях — `TODO`

- [все] **Описание:** правило для `main`: только через PR, обязательные проверки CI, запрет force push.
- **Зависимости:** T-004, T-006. **Оценка:** 0,2.
- **Готово, когда:** прямой push в `main` отклоняется.
- **Проверка:** попытка прямого push.

### T-008 · Вайрфреймы ключевых экранов — `TODO`

- [platform] **Описание:** Android: список объектов, объект, осмотр по комнатам, чек-лист, дефект с камерой, повторный осмотр, сравнение. Web: панель, объект, осмотр, сравнение, отчёты.
- **Цель:** согласовать сценарии до реализации клиентов.
- **Зависимости:** T-001. **Оценка:** 0,5.
- **Готово, когда:** вайрфреймы утверждены владельцем.
- **Проверка:** ревью.

## Неделя 2 — CP1: ядро core-service

### T-101 · Пользователи и аутентификация — `DONE`

- [core-service] **Описание:** регистрация, вход, refresh с ротацией и обнаружением повторного использования, выход, `GET/PATCH /users/me`; Argon2id; JWKS; блокировка после неудачных попыток.
- **Цель:** ADR-007, ADR-008.
- **Зависимости:** T-003, T-006. **Оценка:** 2.
- **Готово, когда:** все сценарии и ошибки из API_DOCUMENTATION покрыты интеграционными тестами.
- **Проверка:** тесты; ручной сценарий REST Assured; проверка cookie-атрибутов.

### T-102 · Авторизация и права на ресурсы — `DONE`

- [core-service] **Описание:** роли ADMIN/INSPECTOR, единый компонент проверки владения ресурсом, ответ `404` на чужие ресурсы.
- **Зависимости:** T-101. **Оценка:** 1.
- **Готово, когда:** для каждого endpoint есть тест доступа к чужому ресурсу.
- **Проверка:** параметризованные IDOR-тесты.

### T-103 · Объекты недвижимости и помещения — `DONE`

- [core-service] **Описание:** CRUD объектов, архивирование, типы, адрес; CRUD помещений с порядком сортировки; оптимистическая блокировка.
- **Зависимости:** T-102. **Оценка:** 1,5.
- **Готово, когда:** API соответствует контракту; валидация полей.
- **Проверка:** интеграционные и контрактные тесты.

### T-104 · Справочники — `DONE`

- [core-service] **Описание:** системные и пользовательские категории дефектов (с переводами), шаблоны чек-листов (7 групп элементов), шкала серьёзности; начальные данные миграцией.
- **Зависимости:** T-102. **Оценка:** 1.
- **Проверка:** тесты; ADMIN может, INSPECTOR не может менять системные категории.

### T-105 · Сервисные токены и внутренний API доступа — `DONE`

- [core-service] **Описание:** client credentials для media/report/ml; `GET /internal/v1/access/properties/{id}`.
- **Зависимости:** T-102. **Оценка:** 0,5.
- **Проверка:** тест: внешний пользовательский токен не принимается внутренним endpoint.

### T-106 · Обработка ошибок, логирование, трассировка — `DONE`

- [core-service] **Описание:** RFC 9457 с кодами ошибок, структурированные JSON-логи, `X-Request-Id`, маскирование чувствительных полей.
- **Зависимости:** T-006. **Оценка:** 0,5.
- **Проверка:** тесты формата ошибок; в логах нет паролей и токенов.
