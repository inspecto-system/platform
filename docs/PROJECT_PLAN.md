# План реализации проекта Inspecto

> Версия плана: 1.0 (этап проектирования, CP0). Обновляется при каждом изменении сроков или объёма.
> Детализация задач — [TASKS.md](TASKS.md). Решения — [DECISIONS.md](DECISIONS.md).

## 1. Цель и результат

Разработать информационную систему для осмотра и приёмки объектов недвижимости: Android-приложение (основной клиент), веб-приложение, микросервисный бэкенд (Java + Go), PostgreSQL, файловое хранилище, генерация PDF-отчётов, сравнение повторных осмотров и ML-подсказка категории дефекта по фото.

**Главный демонстрационный сценарий:** создание объекта → создание осмотра → заполнение чек-листа → фиксация дефектов → фотографирование → PDF-отчёт → повторный осмотр → сравнение результатов → сводная информация.

## 5. Контрольные точки и критерии готовности

Этап считается завершённым только если код проверен, протестирован, прошёл CI, задокументирован и слит владельцем.

| CP | Критерии готовности | Способ проверки |
|---|---|---|
| **CP0** | Документация `docs/` создана; решения ADR-001…021 зафиксированы; контракты OpenAPI v0.1 утверждены; предварительный `INSPECTO_SYSTEM_ARCHITECTURE.pdf`; docker compose поднимает PostgreSQL, SeaweedFS, Gotenberg | Ревью PR владельцем; `docker compose up` без ошибок |
| **CP1** | Регистрация, вход, обновление и отзыв токенов; CRUD объектов и помещений; справочники; права на ресурсы; CI core зелёный, покрытие бизнес-логики ≥ 80 % | Интеграционные тесты (Testcontainers), сценарий REST Assured |
| **CP2** | Через API создаётся осмотр с чек-листом, дефектом, наблюдением и фото; media-service проверяет и сжимает фото | Сквозной API-сценарий; тесты media |
| **CP3** | С телефона проводится полный первичный осмотр, фото на сервере; сравнение осмотров по API покрыто табличными тестами | Ручной сценарий на устройстве + автотесты |
| **CP4** | PDF с фото формируется с телефона; повторный осмотр с отметкой прежних дефектов | Проверка PDF (страницы, текст, шрифты, размер); сценарий на устройстве |
| **CP5** | Веб покрывает просмотр, сравнение и отчёты; базовая проверка ZAP без высоких находок | Playwright E2E; отчёт ZAP |
| **CP6** | Подсказка категории работает сквозным образом и отключается без последствий для сценария | Тест отказа ml-service; метрики в ML_DOCUMENTATION.md |
| **CP7** | Главный демонстрационный сценарий целиком; эксперимент проведён; финальный архитектурный PDF; черновик РПЗ | Демонстрация; данные эксперимента; PDF проверен на открытие и читаемость |

## 6. Порядок сокращения объёма при отставании

Отставание более 3 рабочих дней от контрольной точки запускает сокращение (ADR-001):

1. Редактирование в Web → только просмотр, сравнение и отчёты.
2. ML-подсказки в интерфейсе → остаются исследование и модель.
3. Статистика и графики.
4. Локальные черновики Android.

## 8. Риски

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| Нехватка времени у единственного разработчика | Высокая | Высокое | Порядок сокращения объёма; небольшие PR; раннее обнаружение отставания на каждой CP |
| Качество ML на реальных фото квартир ниже, чем на открытом наборе | Высокая | Среднее | Собственный тест-набор; честный анализ переноса домена; запасное направление (вариант D) |
| Размер и читаемость PDF с фото | Средняя | Среднее | Сжатие фото, отдельный вариант изображения для отчёта, тесты размера и страниц |
| Docker не установлен у разработчика | Средняя | Низкое | Установка Docker Desktop до CP0 |
| Сложность офлайн-режима | Средняя | Высокое | В MVP только черновики, синхронизация — этап расширения |
| Нагрузка CI (Android-сборки) | Низкая | Низкое | Кеширование Gradle, запуск только по изменённым путям |
| Расхождение документации и кода | Средняя | Среднее | Обновление документации — часть критериев готовности каждого PR |
