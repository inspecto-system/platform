## ADR-001. Объём MVP и сроки

**Проблема.** Исходная концепция (`inspecto_detailed.pdf`) рассчитана на 14–16 недель для Android-приложения и монолитного бэкенда. Требования проекта добавили веб-приложение, микросервисы на Java и Go и ML-исследование, при этом желаемый срок — 1–2 месяца. Разработчик один.

**Варианты.**

1. 4 недели на весь объём — нереалистично без потери качества.
2. 8 недель на MVP с фиксированным порядком сокращения объёма.
3. 14–16 недель, как в исходной концепции.

**Решение.** Вариант 2. MVP — 8 недель (2026-11-04 — 2026-12-29), затем этап расширения до дипломной версии.
Если отставание превышает 3 рабочих дня, объём сокращается в порядке:

1. Редактирование в веб-приложении (остаётся только просмотр и отчёты).
2. ML-подсказки в пользовательском интерфейсе (исследование и обученная модель сохраняются).
3. Статистика и графики.
4. Локальные черновики Android.

Стандарты качества кода и безопасности не ослабляются ни при каком отставании.

**Обоснование.** Соответствует приоритетам «качественно и как можно быстрее» и даёт предсказуемый механизм реакции на риски.

## ADR-002. Границы сервисов

**Проблема.** Требуется микросервисная архитектура с использованием Java и Go, но без сервисов «ради количества».

**Варианты.**

1. Монолит на Spring Boot (как в исходной концепции) — не выполняет требование использования Go.
2. Мелкие сервисы по сущностям (properties, inspections, defects, users) — сущности сильно связаны транзакциями; распределённые транзакции резко усложняют систему.
3. Ядро бизнес-логики + выделенные сервисы с другим профилем нагрузки.

**Решение.** Вариант 3:

| Сервис | Язык | Ответственность |
|---|---|---|
| core-service | Java (LTS), Spring Boot | Аутентификация, пользователи, объекты, помещения, осмотры, чек-листы, дефекты, история, сравнение, статистика |
| media-service | Go | Приём, проверка, сжатие, хранение и выдача фотографий |
| report-service | Go | Асинхронная генерация и хранение PDF-отчётов |
| ml-service | Python | Классификация фото дефекта (подсказка категории) |

**Обоснование.** Каждая граница проведена по реальному различию: транзакционная бизнес-логика против обработки файлов (ввод-вывод, CPU на изображениях) против долгих фоновых задач против ML-экосистемы. Отказ media, report или ml деградирует одну функцию, а не всю систему.

## ADR-003. Модель дефекта: Defect + DefectObservation

**Проблема.** Если дефект принадлежит осмотру, при повторном осмотре создаётся новая запись, и сопоставить дефекты двух осмотров по идентификатору невозможно.

**Варианты.**

1. Дефект принадлежит осмотру; сопоставление по описанию/месту — ненадёжно.
2. Дефект принадлежит осмотру, при повторном осмотре копируется со ссылкой на «предка» — цепочки копий усложняют запросы и историю.
3. Дефект принадлежит объекту и помещению; каждый осмотр фиксирует **наблюдение** (`DefectObservation`) этого дефекта.

**Решение.** Вариант 3. `Defect` живёт на уровне объекта. `DefectObservation` — состояние дефекта в конкретном осмотре (`OPEN` или `RESOLVED`), с комментарием и фотографиями. Текущий статус дефекта вычисляется по последнему наблюдению.

**Обоснование.** Сравнение осмотров сводится к сравнению наблюдений одного и того же `defect_id`; история дефекта естественно получается из наблюдений.

## ADR-004. Четыре состояния сравнения

**Решение.** Сравнение осмотра A (базовый) и осмотра B (целевой) одного объекта классифицирует дефекты так:

| Состояние | Условие |
|---|---|
| Новый | В B есть наблюдение `OPEN`, в A наблюдения не было или в A он был `RESOLVED` (тогда дополнительно помечается как «повторно открытый») |
| Устранённый | В A наблюдение `OPEN`, в B — `RESOLVED` (подтверждено пользователем) |
| Оставшийся | В A и в B наблюдение `OPEN` |
| Не проверен | В A наблюдение `OPEN`, в B наблюдения нет |

**Обоснование.** Отсутствие дефекта в новом осмотре не означает его устранения (требование концепции). Устранение фиксируется только явным действием пользователя; замена фотографии не меняет статус.

## ADR-005. PostgreSQL: один экземпляр, отдельные базы

**Решение.** Один экземпляр PostgreSQL 16; базы `inspecto_core`, `inspecto_media`, `inspecto_report`; у каждого сервиса свой пользователь СУБД с правами только на свою базу. Общих таблиц нет. Миграции: Flyway (core), golang-migrate (Go-сервисы).

**Обоснование.** Изоляция данных по принципу database-per-service без затрат на несколько экземпляров СУБД. При необходимости базы переносятся на отдельные экземпляры без изменения кода.

## ADR-006. Файловое хранилище MinIO

**Решение.** Фотографии и PDF хранятся в MinIO (S3 API); в базах — только ключи объектов и метаданные. Бакеты: `photos` (владелец — media-service), `reports` (владелец — report-service). Объекты недоступны извне напрямую, выдача — только через сервисы с проверкой прав.

**Обоснование.** Требование концепции «файлы отдельно, в БД ссылки»; S3-совместимый API позволяет позже перейти на облачное хранилище без изменения кода.

## ADR-007. Аутентификация: JWT RS256

**Решение.**

- core-service выдаёт access-токен JWT (RS256, срок 15 минут) и refresh-токен (непрозрачный, 30 дней, ротация при каждом использовании, в БД хранится только хэш; повторное использование отозванного токена отзывает всё семейство).
- Открытый ключ публикуется по JWKS (`/.well-known/jwks.json`); Go- и Python-сервисы проверяют подпись локально.
- Межсервисные вызовы используют сервисные токены (client credentials, выдаёт core, аудитория `inspecto-internal`).

**Обоснование.** Проверка токена без сетевого вызова на каждый запрос; ротация refresh-токенов ограничивает ущерб от их утечки.

## ADR-008. Хранение токенов в клиентах

**Решение.**

- **Web:** access-токен только в памяти; refresh-токен — cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. Endpoint обновления дополнительно требует заголовок `X-CSRF-Protection: 1` (запросы с другого источника не могут его выставить без CORS-разрешения).
- **Android:** токены в DataStore, зашифрованном ключом из Android Keystore.

**Обоснование.** Защита от кражи токена через XSS (нет доступа из JavaScript к refresh-токену) и от CSRF.

## ADR-009. Ролевая модель

**Решение.** Роли: `ADMIN` (системные справочники, управление пользователями), `INSPECTOR` (полная работа со своими объектами), `CLIENT` (просмотр объектов, к которым выдан доступ). В MVP реализуются `ADMIN` и `INSPECTOR`; частный владелец пользуется ролью `INSPECTOR`. Роль `CLIENT` и выдача доступа (таблица `property_access`) — этап расширения; модель данных проектируется с учётом этого.

Помимо роли, каждый запрос проверяет право на конкретный ресурс (владелец объекта или выданный доступ). Отсутствие права возвращает `404`, чтобы не раскрывать существование чужих ресурсов.

## ADR-010. Синхронный REST между сервисами

**Решение.** Внутренние вызовы — HTTP/JSON (REST) с таймаутами, ограниченными повторами для идемпотентных запросов и сквозным `X-Request-Id`. Брокер сообщений (Kafka, RabbitMQ) не используется.

**Обоснование.** Асинхронность нужна в двух местах — генерация PDF и очистка файлов при удалении; обе решаются таблицей заданий в базе сервиса (ADR-011, ADR-018). Брокер добавил бы компонент без реальной задачи (требование п. 15 промпта проекта).

## ADR-011. Асинхронная генерация PDF

**Решение.** `POST /api/v1/reports` создаёт задание (`QUEUED`) и сразу возвращает `202 Accepted`. Пул воркеров report-service забирает задания через `SELECT … FOR UPDATE SKIP LOCKED`, клиент опрашивает статус. Повторы — до 3 раз с экспоненциальной задержкой.

## ADR-012. Генерация PDF через Gotenberg

**Варианты.** (А) HTML-шаблон Go → Gotenberg (headless Chromium); (Б) программная вёрстка на Go (maroto); (В) JasperReports в core.

**Решение.** Вариант А.

**Обоснование.** Вёрстка через HTML/CSS даёт качественную типографику, кириллицу, управляемые разрывы страниц (`break-inside: avoid`) и колонтитулы. Минус — ещё один контейнер. Gotenberg работает во внутренней сети без выхода в интернет; изображения встраиваются в HTML заранее (защита от SSRF, см. THREAT_MODEL T-12).

## ADR-013. Маршрутизация через nginx

**Решение.** Единая точка входа — nginx (TLS, заголовки безопасности, ограничение частоты запросов, лимиты размера тела). Маршрутизация по ресурсам: `/api/v1/photos/**` → media, `/api/v1/reports/**` → report, остальные `/api/v1/**` → core. Пути `/internal/**` наружу не публикуются. Отдельный API Gateway не создаётся.

**Обоснование.** Клиенты не знают топологию сервисов; для маршрутизации, TLS и rate limiting nginx достаточен.

## ADR-014. Контракты API

**Решение.** OpenAPI 3.1, contract-first. Спецификации хранятся в `platform/api/` и версионируются тегами (`api-vX.Y.Z`). Серверы проверяют соответствие реализации контракту в интеграционных тестах, клиенты (Kotlin, TypeScript) генерируют код из тегированной версии. Ошибки — RFC 9457 (`application/problem+json`).

## ADR-015. Полирепозиторий

**Решение.** Организация `inspecto-system`, публичные репозитории: `platform`, `core-service`, `media-service`, `report-service`, `web`, `android`, `ml`. Общая документация, контракты, развёртывание и переиспользуемые CI-шаблоны — в `platform`.

**Обоснование.** Выбор владельца проекта. Публичные репозитории дают бесплатную защиту веток и неограниченные минуты CI. Риск — открытость кода; компенсируется сканированием секретов (Gitleaks) и запретом коммитить секреты и данные (см. SECURITY.md).

## ADR-016. ML-направление

**Решение.** Основное ML-направление — классификация типа дефекта по фотографии с transfer learning (CNN против ViT) на открытом наборе BD3 и оценкой на собственном тестовом наборе реальных фото. Расширение для диплома — сопоставление фото одного дефекта между осмотрами по эмбеддингам. Оценка серьёзности по фото и OCR отклонены (нет данных / нет исследовательской ценности). Детали — ML_DOCUMENTATION.md.

## ADR-017. Справочники дефектов

**Решение.** Категории дефектов двух уровней: системные (ведёт `ADMIN`, имеют код, используются ML) и пользовательские (видны только владельцу). Серьёзность — фиксированная шкала: `COSMETIC` (косметический), `MINOR` (незначительный), `MAJOR` (значительный), `CRITICAL` (критический).

## ADR-018. Удаление данных

**Решение.**

- Архивирование объекта обратимо (`archived_at`).
- Физическое удаление объекта или аккаунта удаляет записи в core в одной транзакции и создаёт задания очистки в таблице `outbox_events`; фоновый обработчик вызывает внутренние endpoints media и report, которые удаляют записи и файлы в MinIO. Повторы до успеха; задания идемпотентны.
- Неприкреплённые к дефектам фото удаляются media-service автоматически через 24 часа.
- Срок хранения резервных копий ограничен (см. SECURITY.md), поэтому удалённые данные гарантированно исчезают из бэкапов после ротации.

## ADR-019. Локализация

**Решение.** Интерфейс и отчёты на русском. Задел на английский: API возвращает машиночитаемые коды ошибок; названия системных справочников хранятся с переводами (`jsonb`); строки Android — в ресурсах, Web — в словарях next-intl; PDF-шаблоны разделены по локали; у пользователя есть поле `locale`.

## ADR-020. Docker

**Решение.** Docker используется для инфраструктуры разработки (PostgreSQL, MinIO, Gotenberg), интеграционных тестов (Testcontainers), CI и демонстрации (docker compose). Kubernetes и другие оркестраторы не используются.

## ADR-021. Процесс разработки

**Решение.** Каждая законченная функциональная часть — отдельная ветка и Pull Request с описанием (что сделано, как проверить, тесты, известные проблемы). CI обязателен; слияние в `main` выполняет только владелец проекта после ревью. Связанные изменения в нескольких репозиториях — несколько PR со ссылками друг на друга, порядок слияния: контракт → сервер → клиенты. Прямые коммиты в `main` запрещены защитой веток.
